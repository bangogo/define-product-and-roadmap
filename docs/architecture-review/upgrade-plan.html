升级目标

  1. 能力无损：保留当前 72 个 Markdown 契约测试、11 个 HTML 契约测试及场景回归所覆盖的能力，不因架构调整丢失检查项。
  2. 架构精简：收敛为一个验证入口、一份格式无关不变量、HTML 与 Markdown 两个适配层。
  3. 缺陷修复：修复决定记录导出、解析器健壮性、终稿状态校验、迁移覆盖校验四类已确认问题。
  4. 职责分离：机械一致性由脚本执行，产品判断由 AI 完成，最终授权由用户完成。
  5. 可复现验证：升级前后均执行同一组基线测试、缺陷探针、兼容性检查和真实浏览器测试。

执行步骤

  1. 固化能力基线：记录当前全部测试结果与能力清单，作为升级后回归比较的固定输入。
  2. 修复缺陷：先修决定记录导出、结构化错误、嵌套布局误拒、单份 Markdown 入口与终稿矛盾校验，不改变整体架构。
  3. 抽取不变量：将格式无关检查迁入 invariants.py，并建立 HTML 与 Markdown 适配层。
  4. 恢复语义检查：默认采用 S2 粒度，把需求五要素、形态表、证据状态、假设同源、数值基线、迁移覆盖接回默认路径。
  5. 收敛文档：合并重复契约、修复失效引用、移除仓库专属依赖，保持 HTML 权威源不变。
  6. 升级测试：保留现有测试，新增缺陷负例、能力基线回归、真实浏览器测试与 --baseline 用例。
  7. 执行验证：按下一节顺序完成回归、探针、兼容性、渲染与对照测试。

测试验证方案

验证顺序与通过标准
层级验证内容通过标准

2. 缺陷探针 重跑 14 条架构探针 已知坏样本被拒绝；已知误拒通过；异常转为结构化错误
3. 真实浏览器 1440 与 390 视口下的选择、导出与页面状态 导出记录与用户选择一致，且能通过当前校验器
4. 格式兼容 HTML PRD、单份 Markdown PRD、PRD + Roadmap 双文档 三种入口均可用，旧命令与错误语义不意外破坏
5. 迁移基线 --baseline 对旧章节、图、表、需求、规则、链接的 diff 未盘点、未授权删除、重复映射和丢失需求被报告
6. 语义能力对照 同一输入在 v3.2、v4.1、新版本的输出对照 遗漏、无支撑断言、修订保留度和可读性不劣于基线
7. 发布包验证 check_project.py --verify-dist 打包内容、版本、SHA-256 与源码逐文件一致

能力无损检查清单

  • 旧 Markdown 双文档契约：72 项测试全部保留。
  • HTML 独立 PRD 契约：11 项测试全部保留。
  • 增量修订、迁移表、表格/SVG 同步：场景检查全部保留。
  • 决定卡交互与版本级确认：交互测试全部保留。
  • 发布包一致性：项目检查保留。

验收结论标准

  1. 基线测试全部通过，且测试清单与 baseline-test-report.json 一致。
  2. 新增缺陷测试全部通过，14 条探针的预期行为更新为修复后的结果。
  3. 真实浏览器测试在 1440 与 390 视口下通过。
  4. HTML、单份 Markdown、PRD + Roadmap 三种入口的兼容性测试通过。
  5. --baseline 迁移校验能报告未覆盖旧对象、未授权删除和需求映射冲突。
  6. 发布包验证通过，版本记录与 SHA-256 一致。
  7. 验证报告明确区分静态校验、语义自审、真实渲染、真实宿主运行与用户确认。

默认语义检查粒度为 S2。若后续选择其他粒度，只调整第 4 步的检查范围，能力基线与验证顺序不变。

本方案为 Skill 升级执行方案；静态测试通过不构成案例 PRD 内容批准、产品运行证据或发布授权。
