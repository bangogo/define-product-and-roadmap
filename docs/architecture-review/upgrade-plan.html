结论

v4.1 的问题不是“提示词变短了”，而是默认交付格式换成了 HTML，产品语义校验没有跟着过去。 现在的 HTML 分支只查结构、指纹与决定记录；v3.2 已有的需求五要素、形态表、分工、假设同源、数值基线、呈现规则等检查在默认路径上完全不执行。 另一个关键缺陷是真实浏览器里导出的决定记录字段错位，而现有测试全绿，说明验证体系没有覆盖真实交互。

升级方向：保留 HTML 作为唯一权威源，恢复 v3.x 的确定性检查能力，但把架构精简为一个入口、一份不变量、按格式适配。 确定性部分交给脚本，产品判断留给 AI，最终授权留给人。

目标与非目标

目标

  1. 能力无损：v3.2 已有的确定性检查全部保留，v4.1 的合理决策也不回退。
  2. 架构精简：一个入口、一份不变量、按格式适配；不靠拆更多文件制造复杂度。
  3. 缺陷修复：修掉真实交互、解析器、终稿闸门、迁移检查四类已知问题。
  4. 责任清晰：机械一致性归脚本，产品判断归 AI，最终授权归人。
  5. 可复现验收：所有缺陷都有探针，一键重跑。

非目标

  • 不重写案例 PRD。
  • 不改动 Roadmap 的业务语义。
  • 不引入多 Agent 编排器。
  • 不把 prose 全量 JSON 化。
  • 不把 HTML 权威源改成“结构化源 + 渲染”双产物。

架构升级方案

精简的关键不是减少文件数，而是让每层只负责一件事。 用户仍然拿到一份 HTML PRD；AI 仍然做产品判断；脚本只做确定性校验与渲染测量；人只做最终批准。

1. 入口层

SKILL.md 只保留：触发条件、任务分类、关键红线、脚本入口、按需读取的 reference 路由。

2. 契约层

把“产品不变量”抽成单一权威文件；PRD、Roadmap、HTML 工作流只写各自专属内容，不再互相重复。

3. 执行层

脚本负责解析、枚举、指纹、基线 diff、渲染测量；AI 负责语义与取舍；人负责授权。

这个分层让“能不能过校验”和“产品判断是否好”分开，避免把结构完整误当产品质量。

风险与边界

  • 语义检查越深，误报越高。所有新增检查先以警告运行，观察真实误报再决定是否升级为错误。
  • 脚本无法约束其调用路径之外的 Agent 行为。终稿批准与下一闸门授权仍必须由人给。
  • 真实浏览器探针依赖可用浏览器。缺环境时如实写“未验证”，不得把静态检查写成渲染通过。
  • 架构重构可能影响 CLI 兼容性。需同步更新 SKILL.md、check_project.py 与测试。
