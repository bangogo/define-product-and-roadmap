# 定义产品与路线图

交付一份让产品、业务、体验和研发读者能找到用户价值、当前证据、运行逻辑、需求边界、失败恢复与验收依据的产品契约。PRD 默认以**单份 HTML 为权威源稿**；Roadmap 仅在用户需要版本编排时另行交付。旧 Markdown PRD/Roadmap 继续支持审计与校验。

## 按需读取

- 所有产品判断先读 [证据、场景与澄清契约](references/intent-and-scenario-contract.md)。
- 新建、审计或修订 PRD 时读 [PRD 契约](references/prd-contract.md)；HTML 的增量落位、图表和确认操作读 [HTML PRD 工作流](references/html-prd-workflow.md)。
- 需要 Roadmap 时读 [Roadmap 契约](references/roadmap-contract.md)。旧 Markdown 输出还需参考 [Markdown PRD 模板](assets/prd-template.md)；新 HTML 从 [HTML PRD 模板](assets/prd-template.html)按需改写。
- 采纳反馈或重写前查 [修订经验](references/revision-lessons.md)；最终语义评审用 [质量评分表](references/quality-rubric.md)。

## 1. 先确定任务与证据

判断操作是仅审计、新建、增量修订、重写还是与 Roadmap 对齐；确认用户要求的确切文件和交付状态。仅审计不编辑文档。阅读已批准契约、用户已确认决定、当前产物与运行证据、研究及历史材料；把来源、日期、局限和冲突记录在内部台账。

分别判断**产品阶段** A（0→1）或 B（存量迭代），以及**文档操作**是新建还是修改已有文件。产品尚无真实使用，也不能在重写已有 PRD 时省略旧内容继承。B 场景起草前按意图契约七维做只读现状摸排。已确认决策、已观察证据、文档记载、历史证据、建议假设及待调研不能混成当前事实。

建立产品简报：用户和核心任务、价值载体、当前结果、最短价值路径、第一个薄弱转折、已有基础、真值边界、交付目的、审阅人和下一闸门。选唯一主产品形态、不超过两个相关次形态，并单列 AI、发布、敏感数据等风险修饰项。

## 2. 先落位，再改写

修订前盘点旧文的章节、图、表、需求、卡片、有效规则和引用，逐项标注保留、改写、下沉、删除或待确认。把每轮讨论拆成事实、决定、规则、例外与示例，建立“输入 → 唯一权威章节／表格单元／图元 → 关联验收”的落位表。

已有规则改变，就改原规则和验收；同一批对象新增可比较维度，就在原表加列并补齐各行；同一维度新增对象，就加行；流程或责任改变，同步改图和说明。先确认表的行粒度一致，避免无关维度挤入宽表。现有章节容不下新的独立读者问题时，优先补子标题；重大重排先展示新旧目录与迁移表，确认结构后写正文。不要把新讨论按时间追加到文末，也不要重复定义一条规则。

只对会改变产品用户、价值、范围、授权、流程分支、验收或有效历史内容去留的未知项提问。决策卡列现有证据、2–3 个方向、建议、各方向影响和拟落位处。用户已确认的选择可直接应用；未确认项留在审阅稿，不当作已生效产品规则。局部措辞或排版修改不用额外确认。

## 3. 写出产品可执行的 PRD

新建 HTML PRD 可用约 4–5 个主章节组织定位与交付、问题与证据、方案与流程、规则与验收、风险与待确认；这只是导航参考，不是硬性章数。既有文档按内容调整。正文从读者问题出发，先说用户得到什么，再说明输入、系统行为、生效条件、异常恢复和验收；实现命令、写作过程及版本沿革移出产品叙事。产品全景、当前能力、候选能力和具体版本范围分开表述；不凭完整全景推定首版 MVP。

按信息任务选择表达：流程、分支、返工和责任交接优先 SVG；同轴比较用表格；单一规则用短段或需求卡。图先核对节点、连线、阅读顺序与正文对应，再排版。文字不能越框，箭头不能穿字，拥挤时重排或拆图。静态解析不足以宣称视觉通过；桌面、390px 窄屏和打印需实际检查。图中文字和正文名称保持一致，并提供文字替代说明。

每项产品要求写清角色、触发／输入、系统动作、用户可见结果、生效条件、失败恢复及可观察验收。需求 ID 稳定、名称清楚；PRD 写做什么与如何验收，Roadmap 是唯一版本落位处。若只请求 PRD，不为了校验而创建临时 Roadmap。目标数字没有来源时注明候选或待建立基线；不能自动成为放行条件。

## 4. 评审、确认与交付

HTML 审阅稿的决策卡显示证据、选择、建议及影响。用户可逐项选择确认、修改或暂缓，导出带文档 ID、版本、评审 ID 与决定 ID 的 JSON；不预选答案，页面脚本不直接写 PRD。对话中的明确决定也可记入台账。采纳前核对决定记录与**当前审阅稿**完全匹配；过期、未答或默认值不算确认。

静态检查确切文件：

```bash
python3 <技能目录>/scripts/validate_product_docs.py --prd-html <HTML路径> [--decisions <JSON路径>] [--format json]
```

需要 Roadmap 时可加 `--roadmap <Markdown路径>`；旧 Markdown 文档对仍用 `--prd <路径> --roadmap <路径>`。验证器只证明可确定的结构、引用和记录匹配。之后按质量评分表分别完成诉求与继承、单源及跨文档一致性、事实、产品语言与图表的只读评审，并记录实际渲染。阻塞项修复、重验。若用户未确认确切版本的内容和视觉效果，交付状态保持“审阅稿”；只有明确确认后才标最终版。每次只给出一个当前审阅入口，说明版本与前版关系。

文档批准只授权指明的下一闸门，不默示授权实现、真实账户、外部写入或发布。交付时分开报告静态、语义、渲染及用户确认状态。
