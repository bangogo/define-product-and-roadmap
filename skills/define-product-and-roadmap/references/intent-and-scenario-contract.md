## 操作与权限

在改动文件之前,先分类请求的操作:

| 操作 | 允许的结果 | 默认改动规则 |
|---|---|---|
| 仅审计 | 发现、证据、严重度与修复提案 | 不编辑产品文档 |
| 创建 | 新 PRD、Roadmap 或对齐的一对 | 只创建请求的交付物 |
| 重写 | 替换文档加实质性变更摘要 | 通过版本控制或新路径保留原件 |
| 对齐 | 调和已有 PRD/Roadmap 对与当前状态入口 | 只触碰必需文件;保留项目授权 |

记录审阅人、请求的决策与确切的下一闸门。一份产品契约只能授权那个闸门。它不能默示授权 Build、发布、线上账户、敏感数据使用、交易或外部写入（下游常把批准解读为总授权,导致未过闸门即越权执行）。

## 证据与当前效果快照

起草前构建这份内部简报:

| 字段 | 必需结果 |
|---|---|
| 产品用户 | 获得持久产品价值的人或团队 |
| 核心任务 | 产品用户需要完成的、可识别的工作 |
| 当前效果 | 产品当前让用户做到或得到什么 |
| 价值载体 | 收益在哪里变得可见或可用 |
| 价值路径 | 从触发或输入到有意义结果的最短路线 |
| 价值瓶颈 | 阻挡结果的第一个缺失或薄弱转折 |
| 已有基础 | 可工作的页面、产物、数据、接口、服务、Skill 或流程 |
| 真值边界 | 前端、后端、数据、模型、外部服务、人工、权限与产出状态 |
| 交付目的 | 决策演示、用户价值验证、生产改进、集成验证、真实试点或规模化 |
| 审阅闸门 | 审阅人、请求的决策与激活的下一闸门 |

为每条实质性结论维护一份紧凑的证据台账:

| 陈述或观察 | 分类 | 来源 | 日期/版本 | 置信度 | 冲突或局限 |
|---|---|---|---|---|---|

使用这些分类:

- `已确认决策`:已显式批准且仍具权威;
- `已观察证据`:直接检查到的当前行为或产物;
- `文档记载`:由当前文档陈述但未经独立观察;
- `历史证据`:可能有用的先例,但可能过时;
- `建议假设，待确认`:等待决策的可逆或物质性提案;
- `待调研`:无法安全推断的外部或项目事实。

当来源冲突时,仅在确认更高权威、更新的来源仍治理相同范围后,才优先采用它。若冲突改变产品方向或审批条件,发布该冲突。

在 PRD 中使用这张当前效果表:

| 观察对象 | 当前效果 | 证据状态 | 证据来源 | 当前缺口 |
|---|---|---|---|---|

上面的台账分类描述一条陈述从何而来。它们不是运行时真值状态。在发布的当前效果表中,名为 `证据状态` 的列只用规范真值状态 `真实`、`测试接入`、`模拟`、`人工承接`、`仅有文档`、`已观察`、`尚未验证`、`历史证据`。同一组标签适用于每个发布的 `真实性` 单元格。一个目标只有在声明级别有证据后才变为当前。命令退出码、HTTP 200、fixture、transcript 或文档陈述只证明其自身层面。

- [NO] 证据状态单元格填「已完成」「已实现」等自造标签。
- [OK] 证据状态单元格填封闭枚举之一,如 `测试接入`。

## 适用场景判定（A/B）与 B 场景现状摸排

在形态分类之前,先判定文档的适用场景,写入所交付文档的元数据字段 `适用场景`:

- `A（0→1 新产品）`:产品没有可观察的真实使用（证据阶段为想法、静态设计或交互原型）。现状章变形为问题假设与冷启动,复用章变形为外部依赖,无 R0 基线与版本承接。
- `B（存量迭代）`:已有有限真实使用或线上运行。现状章为实测现状,复用章为复用决策注册,路线图含 R0 基线与版本承接。

两场景共用证据分层规则，文档目录依读者问题和现有审阅结构确定；Roadmap 的版本编排规则只在需要 Roadmap 时读取。

A→B 演进承接：当出现可观察真实使用，更新证据状态和现状；若影响产品范围或审批条件，提交决定卡并重过相应闸门。

### B 场景起草前「现状摸排」7 维清单与顺序约束

为存量产品写 PRD 前先只读摸排实际现状。以下维度按产品相关性检查；不适用时说明原因：
1. **交互界面与用户触点**：用户从哪里触发、看到的界面形态、交互反馈链路、易用性与操作断点。
2. **系统流程主链**：从输入/收集、处理/流转到最终呈现/交付的端到端主干链路与卡点。
3. **大模型与脚本分工**：确定性逻辑（脚本/规则）与非确定性生成（大模型）的分工边界，排查模型越权或脚本缺失。
4. **边界条件与兜底**：系统未运行、网络失败、外部无回复、输入为空等异常情况下的兜底与恢复机制。
5. **安装与分发链路**：依赖环境、部署配置、插件/脚本安装、分发交付给使用者时的门槛与摩擦。
6. **知识与资产生命周期**：核心数据与知识资产在系统中的生命周期流转、滞留、积压、归档与归宿状态。
7. **初始化与多项目/多用户扩展性**：首次冷启动成本、模板化配置、多项目共存与未来向多用户扩展的隔离能力。

摸排后列问题、证据与优先级。仅当不同排序会改变产品用户、价值、范围、主流程或验收时，请用户明确选择；其余可作为待验证建议进入审阅稿。

### B 场景快照维护规则

元数据中的 `证据截止日期` 声明当前文档对所依据的证据快照基准：
1. **数字自然漂移不升版**：日常运转产生的正常计数递增（如日志数量上升、数据流水积累），在未改变系统功能、架构或业务语义时，文档不升级版本，保持快照日期不变。
2. **语义或结构变化才升版**：当系统新增/废弃能力、重构业务流程、规则产生实质改变或暴露架构级缺陷时，必须升版（遵循 SemVer）并更新快照。
3. **重大施工前基线重扫**：在任何重大功能施工、存量数据重构或版本正式开工（Proposed/Ready → In Progress）前，必须对系统存量与核心指标进行基线重扫快照，确保施工与验收基于真实最新基线。

## 产品形态分类

通过六个维度分类:

| 维度 | 选项与判据 |
|---|---|
| 主要受益人 | 消费者、业务用户、内部操作人、创作者、开发者、买/卖方或服务人员 |
| 主价值载体 | 消费者界面、内容/产物生产、内部工作流、API/平台、服务编排、交易市场或物理/混合 |
| 证据阶段 | 想法、静态设计、交互原型、测试接入、有限真实使用、线上/规模化 |
| 交付目的 | 决策演示、用户价值验证、生产改进、集成验证、真实试点、规模化 |
| 价值瓶颈 | 理解、激活、任务完成、产物质量、吞吐、可靠性、采用、交接、信任或成本 |
| 风险修饰项 | AI、敏感数据、外部写入、第三方复用/许可、发布、交易、高风险决策 |

从以下选择唯一一个主形态:

- `C端交互产品`
- `内容/产物生产`
- `内部流程工具`
- `API/平台`
- `服务编排`
- `交易/市场`

从同一清单选择不超过两个次级形态。对混合产品,指明主价值载体,而非把每个载体都同等标注。把 AI 与风险条件放进 `风险修饰项`,而非 `次级形态`（风险修饰项才驱动风险控制契约加载,藏进次级形态会使高风险能力无控制行）。

### 形态专属观察视角

| 产品形态 | 首先观察 | 有意义的结果 |
|---|---|---|
| C 端交互 | 页面清单、入口、信息层级、用户路线、状态转移、移动端/可访问性 | 用户完成一个任务并理解结果 |
| 内容/产物生产 | 输入契约、阶段、中间/最终产物、质量、来源、审阅、恢复 | 用户获得一个可用且可审阅的产物 |
| 内部工作流 | 角色、触发、队列、决策、审批、交接、异常、审计 | 操作人完成一个真实工作项 |
| API/平台 | 使用者、入门、首次成功、契约、示例、自助、兼容性、可靠性 | 一个新使用者达到首次成功使用 |
| 服务编排 | 触点、承接方、责任、线上/线下交接、返回与支持 | 用户获得服务结果,而非仅一个链接 |
| 交易市场 | 双方、发现、匹配、信任、交易、履约、结算、争议 | 双方完成一次受保护的交易 |

## 风险修饰项与交付目的

发布零个或多个规范修饰项:`AI`、`敏感数据`、`外部写入`、`第三方复用`、`发布`、`交易`、`高风险决策`。仅在逐项检查后才能使用 `无`（默认填 `无` 会跳过逐项排查,漏配风险契约）。

一个 AI 助手或 Agent 通常是修饰项,而非主形态。检查其触发、上下文、角色、控制、行动边界、输出、不确定性、反馈、回退与评估。交易可以既是主市场载体,又是风险修饰项。

使用这些规范交付目的:

- `决策演示`
- `用户价值验证`
- `生产改进`
- `集成验证`
- `真实试点`
- `规模化`

保持四个角色相互区分:

| 角色 | 完成任务 | 产出的证据 |
|---|---|---|
| 产品用户 | 获得持久产品价值 | 任务、结果、质量或行为证据 |
| 审阅人 | 决定投资或下一交付闸门 | 审批记录与有界的下一动作 |
| 操作人 | 执行人工或运营工作 | 交接、审计或支持证据 |
| 技术负责人 | 交付并维护声明边界 | 接口、状态、恢复与验证证据 |

按以下问题推导优先级:

1. 哪个用户结果最重要?
2. 那个结果在哪里变得可见或可用?
3. 哪些部分已经在工作,应保持为复用依赖?
4. 今天哪个第一转折阻挡了结果?
5. 哪个证据会改变下一个投资决策?

## 提问与分歧工作流

从证据解决项目事实。仅当答案改变用户、价值载体、交付目的、主瓶颈、路线顺序、保真度、真值边界或验收时才提问。

一次只问一个问题:

```text
证据:项目当前展示什么。
建议解读:与证据最一致的方向。
问题:一个高影响选择。
影响:每个答案下什么会改变。
```

当多个方向都仍可信时,对比 2–3 个备选:

| 方向 | 用户价值 | 业务价值 | 可行性 | 差异化 | 证据强度 | 推荐 |
|---|---|---|---|---|---|---|

在发布正式契约前选定一个方向。在 PRD/Roadmap 中只保留所选方向、剩余假设与开放决策。原始对话与被否决选项保留在工作上下文,除非用户要求决策日志。

### 扩展意图作为条件决策

只有证据或请求表明“单实例自用／多项目／分发给他人”的选择会改变本轮目标、范围、交付物或验收，而现有决定又无法回答时，才提交决定卡。可信方向按具体产品证据列出，不把三种模式机械地作为所有 B 场景的必选题。

## 假设登记与完成闸门

在实际交付的文档中发布物质性假设；若同时交付 PRD 与 Roadmap，保持同一权威定义与引用：

| 类型 | 假设或决策 | 状态 | 依据 | 对产品影响 | 确认人/下一步 |
|---|---|---|---|---|---|

规范类型:

- `必须为真`:若为假,所选产品方向失败;
- `重要假设`:实质改变范围或价值,但允许起草;
- `可逆默认`:低风险、可后续更改的选择;
- `高风险外部事实`:需要研究或授权,而非推断。

规范状态:`已确认`、`建议假设，待确认`、`待调研`、`已否决`。

只有已确认项可作为产品事实出现（未确认项写入事实区会被后续会话当作已验证前提放大）。任何未解决或被否决的 `必须为真` 项,使文档保持不具备审批条件（文档状态停在 `Proposed`）。当用户、价值载体、当前效果、交付目的、瓶颈、主路线、真值边界与下一闸门都稳定时停止提问;把实现细节推迟到当前技术 Spec。
