# 产品契约质量评分表

在确定性验证之后使用此评分表。对确切交付的 HTML PRD 或 PRD/Roadmap 对评分,而非其摘要。只请求单份 PRD 时，Roadmap 逻辑与跨文档一致性标为不适用，不为了评分创建临时路线图。

## 评判规则

- 每个维度打 `0`、`1` 或 `2`,并引用文档证据。
- `0`:缺失、矛盾或实质不安全。
- `1`:存在但通用、不完整、证据薄弱或不一致。
- `2`:具体、有证据边界、内部一致且可用于决策。
- 不要用平均分掩盖闸门失败（高分维度不能抵消安全/授权失败,平均分会把不具备审批条件的文档包装为可批）。
- 自审是 `performed`(已执行),而非 `independent`(独立)。仅当全新上下文审查未收到预期答案或隐藏诊断时,它才可能是独立的。

## 维度

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 用户与核心任务 | 用户缺失,或其实是审阅人 | 用户存在但任务/场景通用 | 产品用户、场景、任务、替代方案与优先级都具体 |
| 当前效果与证据 | 目标被呈现为当前,或来源缺失 | 列出现状但证据层面模糊,或未知基线缺最小采集动作 | 当前效果、来源、日期/版本、真值标签与局限相互对齐;每个未知基线带最小基线采集动作 |
| 价值路径与瓶颈 | 用模块清单代替价值交付 | 有路线但第一个薄弱转折不清 | 最短价值路径与第一个瓶颈解释当前优先级 |
| 产品形态匹配 | 通用界面/模块模板占主导 | 命名了主形态但所选契约不完整 | 主/次形态契合价值载体并驱动正确契约 |
| 产品价值与业务逻辑 | 功能声明代替结果 | 收益合理但未连成循环 | 用户结果、业务结果、重复使用理由、证据回流与停止条件相连 |
| 体验/生产完整性 | 仅快乐路径 | 主路径加部分状态或闸门 | 进入、状态、可见结果、失败、恢复、权限与审阅对该形态完整 |
| 复用与归属 | 断言复用却无边界 | 有来源或决策但归属/许可/版本不全 | 来源、版本、许可、证据、决策、适配器、排除项与项目补充都明确 |
| 需求与验收 | 需求是口号或技术任务 | 有 ID 与验收但可观察性弱 | 唯一需求映射到模块,且有可观察的产品与技术证据 |
| Roadmap 逻辑 | 通用功能序列或无证据的日期,或 AI 生成能力直接生成或执行、无评价层 | 命名了版本但问题/退出薄弱,或 AI 能力有评估意图但缺载体、基线采集动作或裁决机制 | 每个版本跟随瓶颈、产出用户价值、回答一个问题并激活一个闸门;AI 生成能力先定义局部评估法再生成,通过裁决后执行 |
| 真值、风险与授权 | 风险或授权被隐藏;暗示不安全动作 | 列出风险但控制/状态不全 | 真值层面、修饰项、控制、未知状态、假设、条件与下一授权都明确 |
| 跨文档一致性 | 存在实质性矛盾 | 存在轻微命名或范围漂移 | 元数据、模块、复用、真值、假设、版本与审批状态对齐 |
| 可读性与决策效用 | 负责人找不到决策，或充斥空话修饰、大段散文重复展开同一论证 | 完整但局部啰嗦（段落 >5 句、出现修饰性套话）或过于技术 | 语言高度精炼（需求一句话主句 ≤2 句，段落 ≤5 句，无填充词），单看目录即可重建逻辑地图，业务/产品/体验/技术负责人能迅速定位决策证据 |

最高分:24。

## HTML PRD 补充评审（不能由静态得分代替）

| 视角 | 必查证据 | 阻塞示例 |
|---|---|---|
| 信息落位与继承 | 旧章节、图、表、卡、需求逐项有保留／改写／下沉／删除／待确认去向；新讨论指向唯一章节、表格单元或图元 | 精简目录时丢失已确认架构图；新增决定只贴在文末而原规则未改 |
| 产品语言 | 每项要求说清用户、触发、输入、可见结果、生效条件、失败恢复与验收；字段名与内容一致 | “系统完成处理”没有用户结果；讨论记录被写成产品规则 |
| 图表语义与视觉 | 图表说明真实关系、阅读顺序、图文同名；浏览器测量和桌面、390px、打印预览记录 | 文字越框、连线穿字、箭头与正文冲突、窄屏无法阅读 |
| 确认与版本 | 决策记录对应当前文档 ID、版本、评审 ID；交付指向唯一审阅稿；用户明确确认确切版内容和视觉 | 预选答案、过期记录、暂缓项或静态检查通过就标最终版 |

分别报告静态结构、产品语义、渲染视觉和用户确认四层结果。静态通过只证明解析及确定性约束；浏览器截图只证明该尺寸的实际显示；语义自审不能假称独立；最终版必须有用户对确切版本的确认。

## 4 视角发布前评审矩阵 Brief

在验证器 0 错误后、文档最终交付前，运行 4 视角只读评审矩阵。每个视角具有独立的输入、检查清单与统一的输出格式（发现分级表）；无独立评审者时标为自审。单文档请求时，视角 2 退化为「文档内一致性」。

### 统一输出格式：发现分级表
每个视角独立输出一张表格：
| 序号 | 发现项 | 严重级别（阻塞 / 建议） | 位置（章节/行） | 事实证据与修改建议 |
|---|---|---|---|---|

- **阻塞（必改）**：破坏契约规则、事实矛盾、编号断链、口径冲突、丢失核心决策。必须在此轮修复。
- **建议（修复或排除）**：措辞精炼度、排版微调、非关键参考补充。可在本轮顺手修复或显式说明排除理由。

---

### 视角 1：诉求覆盖度评审（Scope & Intent Reviewer）
- **输入**：用户所有原始输入（历史发言、决策指令、讨论记录、反馈清单）、生成的 PRD/Roadmap。
- **检查清单**：
  1. 用户所有明确要求的改动、删除、增补是否已 100% 落位；
  2. 用户确认的关键决定（如扩展意图：单实例自用/多项目/分发给他人）是否完整体现在目标与非目标中；
  3. 需求清单与映射表中是否存在断链、漏项或被无故忽略的诉求；
  4. 暂缓或排除的需求是否在非目标或假设表中有明确记录。

### 视角 2：跨文档一致性评审（Cross-Doc Consistency Reviewer）
*(注：若用户仅请求单份文档，本视角退化为「文档内一致性评审」)*
- **输入**：PRD 文档、Roadmap 文档。
- **检查清单**：
  1. **元数据一致**：名称、版本、适用场景、证据截止日期、状态两文档完全一致；
  2. **映射双向对应**：PRD 需求编号与 Roadmap「需求落位映射」双向一一对应，无遗漏无外来；
  3. **口径数值一致**：两文档涉及的指标阈值、观察天数（如「连续 N 天」）、基线数字完全吻合；
  4. **假设表逐字同源**：物质性假设行在两文档中逐字节一致；
  5. **分工不越界**：PRD 需求清单不含版本编码，Roadmap 为落位编排唯一权威。

### 视角 3：现状事实一致性评审（Fact & Truth Reviewer）
- **输入**：真实项目证据源（代码、配置、实测数据、知识库资产、历史日志）、PRD 第 2 章与 Roadmap 第 2/3 章。
- **检查清单**：
  1. **抽样计数核对**：现状章中列出的主要资产数量、文件数、代码行、日志数等与实测基线核对，拒绝编造；
  2. **证据状态合规**：表格中「证据状态/真实性」只使用封闭规范枚举，无自造状态标签；
  3. **存量与增量边界**：存量资产现状与增量改动明确区分，无把目标态当现状的陈述；
  4. **未知基线有采集动作**：每个标为「未知，需建立基线」的项均定义了最小基线采集动作。

### 视角 4：双视角可读性评审（Readability & UX Reviewer）
- **输入**：PRD 与 Roadmap 完整正文。
- **检查清单**（3 分钟四问测试）：
  1. **产品经理视角**：
     - 单看目录能否清晰看懂产品功能边界与各版本交付节奏？
     - 需求块「做什么」是否均为清晰的一句话主句（≤2 句），有无散文啰嗦？
  2. **业务负责人视角**：
     - 3 分钟内能否回答四问：本版承诺什么？最大问题是什么？核心解决思路是什么？下一步怎么判过关？
     - 章节标题是否达意（「对象 + 做什么」短名），有无黑话或无信息废话标题？
     - 段落是否精炼（建议 ≤5 句），修饰性空话（「非常重要」等）是否已彻底剔除？

## 审批阻塞项与质量致命失败

若以下任一审批阻塞项成立,该对文档不具备审批条件:

1. 存在任何未解决或被否决的 `必须为真` 项。
2. 当前行为实质上无支撑、矛盾或误标。
3. 产品用户、主价值载体或所选方向仍混乱。
4. 敏感数据、外部写入、发布、交易或高风险决策缺乏明确授权与恢复。
5. 直接第三方复用缺乏来源版本或许可状态。
6. PRD 与 Roadmap 在产品形态、当前版本、真值、假设或下一闸门上不一致。
7. 当前版本缺乏用户可见的退出证据。
8. 标记 `Complete` 或 `In Progress` 的 AI 生成能力缺少已定义的局部评估法与最小基线采集动作。

一份写得好的产品契约可能正确地保持不具备审批条件。不要仅因为某个审批阻塞项被如实记录就降低语义质量。相反,把以下情况视为质量致命失败:

1. 某个实质性审批阻塞项被隐藏、误标,或与审批条件元数据矛盾。
2. 当前行为被虚构或越出其证据层面。
3. 敏感数据、外部写入、发布、交易或高风险决策在无明确授权与恢复的情况下被授权。
4. PRD 与 Roadmap 实质性互相矛盾。
5. 所选路线无法从陈述的用户价值与瓶颈推导。

## 结果标签

| 结果 | 规则 |
|---|---|
| `semantic_pass` | 至少 20/24,无维度低于 1,无质量致命失败,且每个审批阻塞项都被准确报告 |
| `semantic_conditional` | 至少 16/24 且无未遏制的安全/授权失败,但质量或证据处理仍实质不完整 |
| `semantic_fail` | 低于 16/24,或有任何质量致命失败,或有实质性矛盾 |
| `not_run` | 未审查确切字节 |
| `blocked` | 因缺少必需证据或环境,审查无法运行 |

报告分数、结果标签、审批阻塞项、质量致命失败、最弱维度、所审查的确切版本与审查独立性。绝不要把 `semantic_pass` 转换为运行时证据、用户验证、审批或发布授权（语义审查只覆盖文档内部一致性与证据标注,不产生新证据）。
