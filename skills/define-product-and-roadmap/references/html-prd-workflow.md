# HTML PRD：增量修订、图表与确认

本文件只在创建或修订 HTML PRD 时读取。具体格式见 `assets/prd-template.html`；模板是起点，非固定信息架构。

## 一、把新讨论定位到旧文

先对旧文建立清单：章节、表格、SVG 图元、需求、有效规则、链接和当前证据，各标“保留／改写／下沉／删除／待确认”。对新输入逐条建立记录：来源、内容类型（事实／决定／规则／例外／示例）、确认状态、唯一权威位置、表现形式、关联验收、需同步的图表和文档。

定位规则：

| 变化 | 优先动作 |
|---|---|
| 既有规则的条件、结果或责任变化 | 在原权威位置改原句与验收，其他处只留链接 |
| 同一批对象增加可比较维度 | 在原表加列并补齐每一行，核对行粒度与列语义 |
| 同一维度增加对象或场景 | 在原表加行，并检查相关合计和引用 |
| 主链、分支、回退或责任交接改变 | 修改对应 SVG 节点／连线／图例，并同步表与正文 |
| 原章节容不下一个独立读者问题 | 先核对跨章重复与上位读者问题，再调整子标题或目录；重大重排给出新旧迁移表 |

任何新增表先问：它是否与现有表同一对象维度？若是，合并或引用；若加列使窄屏和打印不可读，用详情卡或关联表。不要把“本轮新增”“补充说明”“再强调”当成正文标题。以用户动作、结果、条件命名标题。交付时让每项输入都能追到章节／单元格／图元及验收。

## 二、产品语言检查

读者只需看到产品行为。每项要求应回答：谁在什么场景下，给什么输入或作什么决定；系统提供什么可见结果；什么条件下生效；失败后用户能怎样继续；怎样观察验收。正文出现“我们刚才讨论”“图上方并列展示”“模块不合格”“消解不确定性”等编辑过程、评论或抽象黑话时，改成具体行为与结果。不要把操作命令、适配器发现、版本沿革塞进产品承诺。

逐段查指代：这／该／它／其指向哪个对象？名称是否在图、表、正文一致？“当前能用”是否有当前证据？候选设计是否被误读为已确认、首版范围或自动放行规则？字段名“创作者动作”下面是否真的只写了动作？需求的验收是否有用户可见状态或产物，而非“功能完成”。

## 三、图表设计与视觉检查

选 SVG 前写出图的读图任务、主链节点、条件分支、回退、责任交接、阅读顺序和与正文的对应。先使信息正确，再布置形状。流程较长可采用多行折返，但用明确编号和跨行箭头；不要预设横版或纵版，已有经用户确认的布局须保留或重新确认。

- 节点标题尽量短；长条件进入邻接表。SVG 使用原生 `text`／`tspan` 明确换行，预留四周内边距。字放不下时增大节点、重排或拆图，不能单靠缩字或压缩字宽。
- SVG 要有 `role="img"`、`aria-labelledby`、`title` 和 `desc`；正文附近给文字版路径或等价表格。箭头方向、分支条件和回退原因可被独立读懂。
- 在浏览器内用 `getBBox()` 或 `getBoundingClientRect()` 测每组文字和所属节点；检查文字边界在节点内边距内，节点／箭头／标签在 `viewBox` 内，连线不穿字、节点不遮挡。`getBBox()` 对 transform 的处理需换算到同坐标系；检查失败时人工读图并记录。
- 分别在桌面、390px 窄屏与打印预览检查整页。窄屏可横向滚动图表，但字号须可读；打印不可裁断关键条件或把全图缩成不可读。记录截图或测量、问题和修复。无浏览器环境时将视觉状态写成“未验证”。
- 表格用 `caption`、`th` 和一致的行粒度；检查单元格换行、横向滚动及打印分割。图表并存时不要在散文中全文复述表格。

静态 HTML 解析只能检查锚点、表格结构、SVG 描述等，不证明几何或视觉质量。图与正文的语义一致性仍由产品读者核对。

## 四、决定卡与终稿

每份 HTML PRD 审阅稿均提供可视化确认入口。无实质待决项时也提供版本级内容、视觉确认和导出入口。有待决项时，每张卡列问题背景、当前证据、可行方向、建议、各方向影响和拟落位处；不足两个可信方向时只展示真实方向，不补虚构选项。决定选项为“确认／修改／暂缓”，初始均不选。“修改”必须留下具体意见，“暂缓”保留未决。页面可查看已选内容并导出 JSON；不用网络提交，不修改 HTML 源稿。键盘可操作，`noscript` 给出对话确认方式。

HTML 的 `main` 带 `data-document-id`、`data-version`、`data-review-id`、`data-status` 和 `data-content-fingerprint`。完成每次源稿编辑后运行 `scripts/stamp_html_prd.py <PRD.html>`，该工具对整份源稿计算 SHA-256，仅将指纹属性自身归一化；因此正文、CSS、脚本或产品元数据改动都会使旧记录失效；仅审批状态从“审阅稿”改为“最终版”被归一化，因此可沿用针对同一内容的有效确认。HTML 模板只作起点，复制后替换示例事实与元数据，再盖章和校验。审阅稿可保留未决；最终版仍须用户对确切修订的内容和视觉明确认可。

导出结构：

```json
{
  "document_id": "example-prd",
  "version": "1.0.0-draft.1",
  "review_id": "review-001",
  "content_fingerprint": "sha256:实际计算值",
  "decisions": [{"decision_id": "D-01", "choice": "修改", "note": "保留人工复核", "source": "web-export"}],
  "review_confirmation": {"content": false, "visual": false}
}
```

采纳前用 `validate_product_docs.py --prd-html <PRD.html> --decisions <record.json>` 核对文档 ID、版本、评审 ID、内容指纹和每个决定 ID。缺项、重复 ID、未选择、预选、修改无具体意见、旧版本或改稿后的旧指纹都不可采纳。`暂缓` 与未完成版本级确认不可标最终版。对话中明确决定可记入同一台账，但该项 `source` 写 `conversation`，不得伪称网页导出；对话也要分别询问内容和视觉是否认可。脚本不可运行时显示文字替代，逐项在对话完成确认，并报告宿主限制。

版本级两个布尔值初始均为 `false`，只有用户针对该修订明确操作才改为 `true`。导出记录、点击“文档已阅”或静态校验通过都不代表产品方向、内容和视觉自动获批。维护者核对记录后更新原权威位置与验收，再重算新修订指纹；如果决定导致源稿变化，需要用户重新确认新修订。每次只交付一个当前审阅入口，并说明批准的下一闸门。
