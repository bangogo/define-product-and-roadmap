## Roadmap 结构（6 章）

在元数据之后、第 1 章之前必须包含「## 目录」节（带锚点列表，见下文「呈现规则呼应」与模板）。正文按以下完整的面向执行顺序（6 章）发布：

1. `用户与终局`:核心用户与任务、当前可见结果、演进目标与终局形态。
2. `现状与总路线`:一句话基线、基线数字（子弹式）、能力优先级（白话主句在前、编码句为注）、总路线与并行试点。
3. `本版详单`:当前提议版本的范围与不包含、交付清单与验收、真值边界表（truth 表唯一权威处）。
4. `体验版本路线图`:一句话路线总述、版本总表（每格 ≤1 句）、每版详述（任务/你会看到什么/为什么有效/增量/进入退出条件）、需求落位映射。
5. `能力层级`:读法声明（L0/L1/L2=成熟度等级,与流水线步骤无关）、层级表。
6. `闸门与假设`:版本闸门表（含白话列）、假设登记（与 PRD 逐字同源）。

## 呈现规则呼应

Roadmap 严格遵循 PRD 契约定义的 12 条呈现规则，重点强化以下三条：
1. **目录即地图（规则 11）**：在元数据之后、首个正文 H2 之前必须包含「## 目录」节（带锚点列表）。目录行与实际 H2/H3 标题逐字一致；单看目录应能重建文档执行地图（总-分：定位终局 → 现状与总路线 → 详单真值 → 版本演进 → 能力层级 → 闸门治理）。章节标题必须达意（「对象 + 做什么」），禁黑话标题与「其他」「杂项」类无信息标题。
2. **语言精炼（规则 12）**：任务说明、增量描述保持一句话主句；正文段落建议 ≤5 句，同一论证不在散文中重复展开（单源化收口到句段粒度）；删除修饰性空话。
3. **不写工期估计（规则 9）**：维持「不写日历时间」规则，版本关系只表达依赖顺序与时点口径，严禁标注人天、工期估计、周数或具体上线日期。日期承诺无证据支撑且随时间失效，依赖顺序才是可校验的编排权威。

## 各司其职:需求落位映射是唯一权威

- PRD 按优先级（P0/P1/P2）组织需求、只定做什么与怎么验收、不标版本。
- Roadmap 的「需求落位映射」表是每条需求落位到版本的**唯一权威**,须在表前显式声明。每条需求进入哪个版本只在本表维护;PRD 与 Roadmap 其他章节不再重复编排。
- 映射格式:每版本一行,列出落位该版本的 PRD 需求编号;或每需求一行、版本一列——同一次文档对内保持一种（两种格式混用使验证器无法做机械比对）。
- 硬规则（验证器错误级校验,完整规则见 PRD 契约「各司其职」）:映射与 PRD 需求编号双向一一对应。

## 能力语言

使用:

| 编码 | 含义 |
|---|---|
| `A「模块」` | 持久产品模块 |
| `A0「能力」` | 模块 A 内具名的成熟度等级 |
| `R1（第 1 个体验版本）「名称」` | 第一个体验版本 |

在每个决策点把编码与名称一起重复。一个能力定义责任、输入、用户可见输出、归属边界与退出证据。定义每个模块的成熟度等级:

给每个模块分配不同的大写字母。能力编码继承该字母:`A「采集」` 可包含 `A0「手工采集」`,而另一个独立的 `B「审阅」` 模块用 `B0「人工审阅」`。不要把 `A` 复用于多个不同名称的模块。闸门标识用 `GT*` 前缀（如 `GT2（第 2 道版本闸门）`）,不是能力编码。

散文中的阶段范围、模块与能力枚举只引用编码;完整清单以 `能力层级` 与 `体验版本路线图` 两张权威表为准,不在散文中重列,防止两处漂移。散文出现权威表未定义的编码是错误。

| 产品模块 | L0（第一级） | L1（第二级） | L2（第三级） |
|---|---|---|---|

不要给每个模块分配相同的等级递进,不做同构递进（不同模块的同级能力含义不同,不能横向比较）。每个等级必须代表其自身责任上可观察的改进;超出本文档视野的等级由最后一道闸门激活下一轮路线图修订时排期,不悬空承诺。

## 按价值载体选择路线

从第一个缺失或薄弱的转折推导路线,而非从默认模块顺序。

### C 端交互产品

把一条可用路线串起来:进入、理解、行动、状态变化、可见结果与恢复。仅当某个页面本身能解决一个有意义的产品决策时,才建立独立的页面版本;否则保持端到端可点击路径。

### 内容或产物生产

当某个模块的产出可独立使用、可保留、可比较且可验收时,让它独立成版。一个有效模式是:

```text
参考基线 → 独立模块升级 → 集成 → 恢复 → 历史/复用
```

基线证据不批准生产复用（评审样本是受控输入,不代表生产分布下的表现与许可边界）。集成保留独立的产物契约与来源。

### 内部流程工具

把一个真实工作项串起来:触发、处理、交接/审批、结果、异常与审计。优先一个端到端队列项,而非分离的前端/后端里程碑。

### API 或平台

把可发现性、入门、首次成功、可重复集成、自助、可靠性与采用串起来。版本以使用者拥有的成功使用退出,而非仅一个已实现的端点。

### 服务编排

把进入、承接方交接、结果或状态返回、失败恢复、更多服务场景与真实集成串起来。

### 交易/市场

在扩展流动性、匹配深度、自动化或变现之前,先完成一次双方受保护的交易。

### 决策演示

当直接目的是投资或管理层对齐时,使用有界演示。标注固定数据、模拟服务、人工准备与演示辅助。演示仍须展示产品用户的任务;审阅人的讲解仍是交付支持。

## 版本与证据规则

版本总表（每格 ≤1 句,增量细节移入每版详述）:

| 版本 | 一句话任务 | 你会看到什么（对比上一版） | 状态 |
|---|---|---|---|

每版详述按固定小节:`任务`、`核心能力`、`你会看到`、`为什么有效`、`本版增量（动作→感知）`、`主要验证问题`、`进入条件`、`退出条件`。

`R0「当前基线」` 仅用于已观察或有文档记载的当前状态（B 场景专属;A 场景无 R0）。计划版本从 R1 起连续编号（跳号会中断版本承接链与验证器的连续性检查）。使用规范状态值:`已有`、`Proposed`、`Ready`、`In Progress`、`Blocked`、`Complete` 或 `Superseded`。

对每个非零版本:

1. 描述一句完整且有意义的用户体验。
2. 验证一个会改变决策的主要问题。
3. 把已接受的路线与产物保留为回归基线。
4. 把可工作的资产作为复用依赖携带,直到某个具名缺口证明需要改动。
5. 替换一个或少数真值边界。
6. 把前端、后端、数据、模型、接口、集成与测试工作放在体验版本之下。
7. 声明带证据的进入与退出条件。
8. 指明退出证据激活的闸门。
9. 在试点证据支持一个有界版本前,把规模化与变现作为方向。

形态专属的退出证据:

| 产品形态 | 版本退出证据 |
|---|---|
| C 端交互产品 | 可点击路线、状态与恢复证据、理解或任务证据 |
| 内容/产物生产 | 可用产物、质量结果、来源、审阅与重放证据 |
| 内部流程工具 | 完成的工作项、交接/审批、异常与审计证据 |
| API/平台 | 新使用者首次成功、契约检查、可靠性与入门证据 |
| 服务编排 | 承接方交接、可见结果/状态、返回、责任与恢复证据 |
| 交易/市场 | 双方完成、信任、履约/结算与争议证据 |

不要仅凭任务完成、退出码、HTTP 响应或文档批准就把版本标记为 `Complete`。要求该版本声明了用户可见结果与退出证据。

### 评价先行

对 AI 生成类能力使用默认优先序 `先评价 → 再生成 → 后执行`;只有证据能推翻该顺序时才重排,并说明依据。

1. 先评价:定义局部评估法——评估载体、评估维度、裁决机制与解锁条件;先给一组真实样本让评审者建立最小基线。
2. 再生成:生成面向该评估优化的候选,并与基线比较。
3. 后执行:通过裁决机制后,才解锁面向用户的执行。

每个引入 AI 生成能力的体验版本,在 `主要验证问题` 中声明该版本的局部评估法。成功信号全部 `待验证` 而无最小基线采集动作的版本,不得标记 `Complete`。

## 施工期运行兼容（B 场景）

在存量系统演进过程中，系统在施工期间仍在运行且数据持续产生。为防止施工动作与日常运行冲突、避免验收基线漂移，必须严格遵守以下口径：

### 1. 三时点口径
1. **基线锚定执行日快照**：存量清理、数据迁移或规则关账类动作，其存量基准以**执行日快照**为准；其后新产生的数据严格走既有日常机制，绝不反复回扫设置二次批量。
2. **验收锚定验收时点**：退出验收以**验收时点**的实际快照与指标进行判定；验收窗口内的新增数据由当日正常运转机制即时消化，存量或异常数据若发生回涨则直接判定为退出失败。
3. **连续 N 天窗口起算点**：验证稳定性与日常运转的「连续 N 天」观察窗口，各自从对应交付项**合入上线日**起算；施工期间仍走老路径的历史天数一律不计入该窗口。

### 2. 存量与增量分界
明确区分「存量一次性处置」与「增量持续保障」：存量清理有明确的执行范围与完成标志；增量保障通过日常触发器、钩子或定时规则运行，两者边界清晰，互不干扰。

### 3. 安全网先行与合入顺序
- **安全网先行**：回滚点（数据备份、恢复脚本）、git commit 检查点、必要的可观测性（日志/监控/排障入口）类交付项必须最先合入。
- **逐项合入与观察**：核心行为项与业务逻辑变更必须逐个合入，每项合入后在真实环境中观察 ≥1 天，确认无破坏性回归后再合入下一项。
- **状态流转**：版本正式开工时，版本状态由 `Proposed` 或 `Ready` 显式变更为 `In Progress`。
- **不写工期估计**：严禁在文档中添加人天、人月、上线周数等工期估算；仅依靠依赖顺序、安全网检查与验收时点门禁把控进度。

## 本版详单与真值边界

展示当前活跃或提议版本的确切交付物:

| 交付项 | 用户可见结果 | 当前实现 | 真实性 | 验收证据 |
|---|---|---|---|---|

验收证据引用每版详述的退出条件,不重贴。

真值边界表（当前版本范围与真实性）在此发布——这是两文档唯一权威处（自 PRD 移入,PRD 不再有真值边界表）:

| 层面 | 当前实现 | 真实性 | 用户可见标识 | 后续替换 |
|---|---|---|---|---|

覆盖每个适用层面:前端或任务界面、后端/流程、数据/输入、模型、外部服务、人工支持、产出质量与发布/交易状态。A 场景允许全为「尚未验证/模拟」,但表必须存在——「什么都还没实现」本身是要显式声明的真值。

在使用点声明规范真值标签（8 个封闭枚举见意图契约;「真实性」列取值同「证据状态」）。

### 执行就绪结论（施工前闸门）

进入版本施工前，闸门评审必须产出明确 verdict（执行就绪裁决）：
- `可施工`：施工前检查单全部通过，授权版本状态从 Proposed/Ready 变为 In Progress；
- `先补 X`：存在阻塞项，必须先补齐 X 后再裁决，严禁带着阻塞缺口开工。

施工前检查单（5 项必核）：
1. **安全网先行**：回滚点、git commit 记录点、必要的可观测性日志/指标交付项已就绪且最先合入。
2. **回滚机制**：各交付项变更具备独立或成组回滚方案，异常时可在规定时间内恢复至开工前基线。
3. **时点口径对齐**：存量清盘基线（执行日快照）、退出验收时点、连续 N 天观察窗口起算点（合入上线日）已明确无异义。
4. **验证器 0 错误**：PRD 与 Roadmap 文档对经验证器脚本校验 0 错误（含标题与目录一致、需求映射一一对应等）。
5. **授权链闭环**：该版本对应的前置闸门已有决策人明确批准记录，无跨版本超范围施工。

### 状态与授权口径

状态口径声明:文档状态、版本状态、运行时真值、外部操作状态与审批条件相互区分:

- 文档状态:Draft、Proposed、Review Candidate、Approved 或 Superseded;
- 版本状态:已有、Proposed、Ready、In Progress、Blocked、Complete 或 Superseded;
- 运行时真值:真实、测试接入、模拟、人工承接、仅有文档、已观察、历史证据或尚未验证;
- 外部操作状态:未尝试、进行中、已确认、失败或未知;
- 审批条件:对所指明的闸门已具备或未具备。

批准仅激活所指明的下一闸门,不构成对后续版本实现、对外发布或自动扩围的授权。

修订史与考古括号禁令、散文重列枚举的限制见 PRD 契约「呈现规则」;清单以权威表为准。

## 验收

1. Roadmap 以产品用户的任务与当前证据基线开篇（A 场景为起点声明）。
2. 路线跟随主价值载体与第一个价值瓶颈。
3. 每个编码在使用点带名称。
4. 每个版本产出形态匹配的证据,并回答一个主要问题。
5. 已有的可工作资产保持为复用依赖,直到某个具名不确定性激活工作。
6. 后续版本保留已接受的用户路线或产物契约。
7. 审阅人、演示辅助与技术任务保持在产品版本之下。
8. PRD 与 Roadmap 共享元数据（含适用场景）、术语、范围、复用决策、真值、假设与授权状态。
9. 本版详单声明用户可见交付物、排除项、证据与确切的下一闸门。
10. AI 生成能力遵循「评价先行」节（同文档「版本与证据规则」内）定义的优先序与声明要求。
11. 需求落位映射与 PRD 需求编号双向一一对应,且为本对文档中唯一的版本落位编排处。
12. B 场景施工期版本必须明确三时点口径与安全网先行顺序，开工前闸门评审必须包含明确执行就绪裁决（verdict）与施工前检查单。
